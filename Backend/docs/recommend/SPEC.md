# 추천 엔진 명세 (MVP v2)

`Backend/src/` 의 배달 최적화 추천 엔진 명세. 크롤러/데이터 파이프라인이 만든 가게·메뉴 데이터 위에서, 유저의 키워드/취향/상황을 받아 **음식(1단계) → 음식점(2단계)** 2단계로 추천한다.

> 이 문서는 설계 토론(PHASE 1~6) 합의를 코드 구현 계약으로 고친 v2다. v1 대비 변경점은 [§11 v1→v2 변경 이력](#11-v1v2-변경-이력) 참조.

---

## 1. 시스템 핵심 원칙

| 원칙 | 내용 |
|---|---|
| **독립성** | 유저 입력 키워드(상황/환경)는 **1단계(음식 추천)에서만** 작동하고 소멸한다. 2단계(음식점 랭킹)에는 절대 누설되지 않으며, 오직 CF 그룹 선호도 + 가용성(영업)·거리·개인 필터만 쓴다. (데이터 파편화 방지) |
| **연속성** | 내부 연산은 소수점 기반 실수 좌표계(`-1.0 ~ +1.0`)를 쓴다. 마이페이지 표시만 16종 맛 MBTI 코드로 변환한다. |
| **환경 인지** | 외부 환경(시간/날씨/온도)은 백엔드 진입 직전 **상황 키워드로 이산화**해 시스템이 계절성을 자동 학습하게 한다. |
| **점진 전환 (콜드 스타트)** | 데이터가 0건이어도 **콘텐츠 기반**으로 추천이 돈다. CF 데이터가 쌓이는 만큼 CF 비중이 자라는 **블렌딩** 구조다. 스위치를 한 번에 바꾸지 않는다. |

---

## 2. 맛 좌표계 정의

### 2.1 5축 정의 (음식 좌표)

음식(`dishes`)은 **5축 실수 좌표**(`-1.0 ~ +1.0`)로 표현한다.

| 축 | -1.0 | +1.0 |
|---|---|---|
| `spicy` (매운맛) | 안 매움 | 매우 매움 |
| `sweet` (단맛) | 안 닮 | 매우 닮 |
| `salty` (짠맛) | 슴슴 | 매우 짬 |
| `oily` (기름짐/진함) | 담백/맑음 | 기름짐/진함 |
| `temp` (온도) | 차가움(냉면·회) | 뜨거움(국밥·찌개) |

### 2.2 축 역할 분리 (중요)

> 온도는 **"나의 고정 입맛"이 아니라 "오늘의 상황"**이다(겨울 국밥 ↔ 여름 냉면은 같은 사람도 매번 바뀜). 따라서 축을 용도별로 분리한다.

| 대상 | 차원 | 비고 |
|---|---|---|
| **dishes (음식)** | 5축 (온도 포함) | 음식의 객관적 속성 |
| **Users (유저 프로필) / 16 MBTI** | **4 미각축** (`spicy/sweet/salty/oily`) | 안정적 입맛만. `temp` 제외 → 2⁴=16 그룹 |
| **ContextKeywords (키워드)** | 5축 (온도 포함) | `#폭염`은 `temp` 음수, `#한파`는 양수 |

**쿼리 시점 타겟 벡터 생성:** 유저 프로필(4축, `temp`=0 중립) + 키워드 벡터(5축)를 가중 평균해 **5축 타겟 벡터**를 만든다. → 온도축은 오직 환경/키워드가 채운다. → 이 5축 타겟과 `dishes` 5축 좌표의 **코사인 유사도**로 메뉴를 정렬한다.

### 2.3 16 맛 MBTI (표시 + CF 그룹)

- 4 미각축 각각을 `0` 기준 이진 분할 → `2⁴ = 16` 그룹 코드.
- **CF 연산은 MVP에서 16버킷 사전 집계로 구현**(단순·빠름). 유저 수가 충분해지면 **연속 좌표 kNN**으로 전환 여지를 둔다(§9.4).
- **마이페이지 표시 = CF 그룹 = 동일한 16코드** (MVP 단계). 표시용 라벨과 CF 연산 분리는 후순위.

## 3. 데이터베이스 스키마 (개념 설계)

> 물리 DB 파일 배치(단일 `app.db` vs 도메인별 분리)는 구현 시 결정. 아래는 논리 테이블.

### 3.1 유저 / 취향 레이어

**Users (유저 마스터)**
```
[user_id, name,
 pref_spicy, pref_sweet, pref_salty, pref_oily,   -- 4 미각축 (-1.0~+1.0)
 mbti_code,                                        -- 16 그룹 코드
 onboarding_done,                                  -- 설문 완료 여부
 updated_at]
```

**UserTagLogs (암묵적 CF / 개인 소비 장부)**
```
[user_id, tag_name(dish_id 또는 카테고리),
 cumulative_count, last_consumed_at]
```
- 시간 감쇠(§10) 대상. **개인 부스트(§7.4)의 근거 장부**이기도 함.

### 3.2 음식 / 키워드 레이어

**dishes (추상 음식 마스터)** — 좌표가 붙는 곳은 가게 메뉴가 아니라 여기.
```
[dish_id, dish_name(짜장면/탕수육/라멘/마라탕),
 category(한식/중식/일식/양식/...),
 spicy, sweet, salty, oily, temp]                 -- 5축 좌표
```

**menu_dish_map (정규화 다리)** — 크롤링 실메뉴 → 추상 음식.
```
[menu_id 또는 (store_id, menu_name), dish_id, confidence]
```
- `details.db / menus.menu_name`("프리미엄마라탕(소)") → `dish_id`(마라탕) 매칭. LLM 일괄 정규화로 채움(§9.3).

**ContextKeywords (상황/환경 키워드 가중치)**
```
[keyword_name(#스트레스/#폭염/#한파),
 keyword_type('direct_taste' | 'context'),        -- 가중치 차등(§8)
 w_spicy, w_sweet, w_salty, w_oily, w_temp,        -- 5축 가중치
 settle_log_count]                                 -- 누적 정산 로그 수
```

### 3.3 집단지성(CF) / 제어 레이어

**GroupRestaurantPreferences (16그룹 × 음식점 장부)**
```
[mbti_code(16종), store_id, dish_id,
 order_count]                                      -- 평점 제거, 주문 횟수만(§7.5)
```
- 2단계 음식점 추천의 CF 핵심. 동일 그룹 유저들의 주문 로그 누적.

**UserNegativeFilters (음식 개인 제어)**
```
[user_id, dish_id, is_ban, penalty(0.0~1.0), updated_at]
```

**UserRestaurantFilters (음식점 개인 제어)** — *신설.*
```
[user_id, store_id, is_ban, coefficient(0.0~2.0), updated_at]
```
- `coefficient`: `<1.0` 감점 / `1.0` 중립 / `>1.0` 선호 부스트 / `is_ban` 차단.
- 선호 **음식점**은 CF(그룹 평균)가 못 잡는 개인 단독 신호라 별도 저장. (선호 **음식**은 `UserTagLogs`로 충분하므로 불필요.)

### 3.4 자가 진화 레이어

**KeywordUpdateBuffer (정산 버퍼)**
```
[buffer_id, input_keyword, selected_dish_id, track('A'|'B'|'C'), created_at]
```
- 낮 동안 순수 텍스트 적재. 새벽 배치가 소비(§9).
- `track` 기록: **Track A는 사전 학습에서 제외/약화**하기 위한 플래그(§7.1).

## 4. 콜드 스타트 → CF 블렌딩

### 4.1 음식 추천(1단계)
- CF 없이도 **완전 작동**. 온보딩 설문(§5)으로 유저 4축 벡터 + `dishes` 좌표만 있으면 코사인 유사도로 추천 가능.
- CF(`UserTagLogs` 개인 부스트)는 여기서 "있으면 더 좋은" 가산 요소일 뿐, 전제 아님.

### 4.2 음식점 추천(2단계) — 진짜 콜드 스타트 지점
```
최종점수 = (1 - w) × 콘텐츠점수 + w × CF점수
w = min(1.0, 그룹_내_주문수 / N_THRESHOLD)
```
- 주문 0건 → `w=0` → **순수 콘텐츠 폴백**: `(영업중 필터) → 거리 → (있으면) 평점` 순.
- 그룹 주문이 쌓이면 `w → 1` 로 CF 비중 점증. `N_THRESHOLD`는 그룹별 튜닝값(초기 제안: 30).

---

## 5. 온보딩 설문 → 초기 취향 벡터

- 가입 시 몇 문항으로 유저의 **4 미각축 초기 좌표**를 산출 → `mbti_code` 배정. (유저 쪽 콜드 스타트 해법)
- 각 문항을 축에 매핑(예: "매운 음식을 얼마나 즐기나요?" → `pref_spicy`).
- 프론트/백 인터페이스: 프론트가 설문 응답 → 백엔드가 좌표 변환·저장. (프론트는 현재 자유 텍스트 태그 모델 → 백엔드 5축 좌표 변환 레이어 필요. §11)

## 6. 메뉴 정규화 파이프라인

```
details.db / menus.menu_name (실메뉴, 들쭉날쭉)
    │  LLM 일괄 정규화 (§9.3)
    ▼
menu_dish_map  ──→  dishes (추상 음식 + 5축 좌표 + 카테고리)
```
- 추천 엔진이 "마라탕"을 골랐을 때, `menu_dish_map`을 역추적해 **마라탕을 파는 가게**를 2단계 후보로 올린다.
- Track A("삼겹살" 직접 입력)의 메뉴 고정도 이 정규화가 선행돼야 동작.

---

## 7. 라우팅 명세 (트랙 A/B/C)

### 7.1 Track A — 구체적 메뉴명 유입 (예: `삼겹살 #개닦임`)
1. **1단계 음식 추천 통째 스킵.** 메뉴를 `삼겹살`(dish_id)로 고정.
2. 2단계 음식점 정렬: 추가 키워드(`#개닦임`)는 랭킹에 **절대 미반영**. CF + 가용성·거리·개인필터만.
3. 버퍼 적재: `(#개닦임, 삼겹살_id, track='A')`.
   - ⚠️ **Track A는 사전(ContextKeywords) 학습에서 제외 또는 약한 가중치.** 키워드가 선택을 유발한 게 아니라 유저가 메뉴를 이미 정했으므로 인과가 약함(Phase 4 오염 방지와 일관).
   - 단, **개인 로그(`UserTagLogs`)에는 정상 적재** → 다음부터 삼겹살이 개인 추천에서 잘 뜸(§7.4).

### 7.2 Track B — 대분류 카테고리 유입 (예: `중식 #한파`)
- 1차 후보 풀을 카테고리로 강제 제한(`WHERE category='중식'`) 후, 그 풀 안에서만 1단계 코사인 연산.

### 7.3 Track C — 추상/환경 키워드 유입 (예: `#스트레스`)
- 키워드 가중 평균(§8) → 5축 타겟 벡터 → `dishes`와 코사인 유사도 → 메뉴 도출 → 2단계 진입.

### 7.4 개인 부스트 (모든 트랙 공통, 1단계)
```
음식점수 = 코사인유사도 + β × 개인선호(UserTagLogs[dish], 시간감쇠 적용)
```
- 16그룹 CF와 **무관한 나 개인의 가산점**. "내가 자주 먹은 음식"이 그룹과 상관없이 위로.

### 7.5 음식점 가용성 (2단계, 필수)
- **하드 필터:** `business_hours` 기준 "지금 영업중"이 아닌 가게는 후보 제외. (특히 `#야식타임`)
- **소프트 페널티(선택):** 라스트오더 임박 감점.
- 키워드 누설이 아니라 **가용성 필터**이므로 독립성 원칙과 충돌 안 함.

### 7.6 주문 횟수 수집
- 어플의 "최종 주문 결정 저장" 기믹 → `GroupRestaurantPreferences.order_count` + `UserTagLogs` 자동 적재. CF의 핵심 연료.
- **명시적 평점은 MVP 제외.** 부정 신호는 `UserNegativeFilters`로 대체.

## 8. 키워드 처리 (2계층)

| 시점 | 처리 |
|---|---|
| **실시간 (유저 입력 순간)** | LLM 호출 금지(타임아웃). **시드 사전 조회**로 즉시 처리. 모르는 키워드 → 중립(`context`, 기본 가중치)으로 처리하고 버퍼 적재. |
| **새벽 배치** | sLLM이 버퍼의 미분류 키워드를 `keyword_type` 분류 + 좌표 추정해 사전 편입(§9). |

- `keyword_type`별 가중치(가중 평균):
  - `direct_taste` (직접 맛, 예 `#매운맛`·`#단짠`): **`W=1.5`**
  - `context` (상황/감정/환경, 예 `#스트레스`·`#폭염`): **`W=1.0`**
- 단순 평균 시 강한 의도가 부가 성분에 희석되는 문제를 차등 가중으로 방지.
- "유저 직접 추가 키워드는 미리 지정된 맛 키워드로 처리" = 이 **시드 사전 매칭** 경로.

## 9. 새벽 배치 정산 (백오피스)

### 9.1 sLLM 문맥 검증 (검증관, 계산기 아님)
- 새벽 3시 가동. `KeywordUpdateBuffer` 데이터셋의 문맥적 타당성을 sLLM이 **True/False(또는 JSON) 필터로만** 판정. 악의적 오염 노이즈 차단.
- ⚠️ sLLM에 숫자 연산을 시키지 않는다(환각/형식 깨짐/타임아웃 방지).

### 9.2 EMA 정산
- 검증 통과 데이터의 평균 맛 좌표를 **파이썬이 계산** → 기존 `ContextKeywords` 가중치에 완만 반영.
  ```
  new = (1 - α) × old + α × batch_mean,   α = 0.05
  ```
- Track A 적재분은 제외/약화(§7.1).

### 9.3 메뉴/좌표 LLM 일괄 라벨링
- (a) `menu_dish_map` 정규화, (b) 신규 `dishes`의 5축 좌표 초기 추정을 같은 sLLM 도구로 배치 처리.

### 9.4 (후순위) CF 그룹 방식
- MVP: 16버킷 사전 집계. 유저 수 증가 시 **연속 좌표 kNN**(쿼리 시점 최근접 k명의 주문 장부 집계)로 전환 검토 — 16버킷의 경계/빈칸 문제 완화.

---

## 10. 시간 감쇠

- `UserTagLogs` / `ContextKeywords` 신선도 보정. 표준 지수 감쇠로 시작(추후 튜닝):
  ```
  effective = base × 0.5 ^ (elapsed_days / HALF_LIFE)   # HALF_LIFE = 30일 (초기값)
  ```
- 스키마는 `last_consumed_at`만 확보. 정확한 공식·반감기는 구현 단계에서 확정.

## 11. v1→v2 변경 이력

| # | 변경 | 근거 |
|---|---|---|
| 1 | `UserRestaurantFilters` 신설(BAN/감점/선호 통합 계수) | 음식점 개인 제어 부재 |
| 2 | 콜드 스타트 → CF **블렌딩 공식** (`w = min(1, 주문수/N)`) | 데이터 0건에서도 작동 |
| 3 | 온보딩 설문 → 초기 4축 벡터 | 유저 쪽 콜드 스타트 |
| 4 | `dishes` + `menu_dish_map` 정규화 레이어 | 추상 음식 ↔ 실메뉴 다리 부재 |
| 5 | 맛 축 4 → **5축**(매운/단/짠/기름/온도), 트렌디함 제거, **온도=환경 전용** | 냉면/국밥 등 온도·단맛 구분 불가 |
| 6 | 개인 부스트(`UserTagLogs`) 명시 + **Track A 사전 학습 제외** | Phase 4 오염 방지와 일관 |
| 7 | 음식점 **영업중 하드 필터** | 닫힌 가게 추천 방지 |
| 8 | 주문 횟수만 수집, **평점 제거** | MVP 공수 절감 |
| 9 | `keyword_type` + 시드 사전/배치 분류 2계층 | 실시간 LLM 호출 금지 |
| 10 | `last_consumed_at` + 감쇠 공식(반감기 30일) | 신선도 미정의 |
| 11 | CF는 16버킷(MVP)/kNN(후순위), MBTI 4축 | 5축↔16그룹 산술 정리 |
