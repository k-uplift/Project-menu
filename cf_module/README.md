# me:nu CF Recommendation Module

me:nu는 성북구 일대 식당을 추천하는 캡스톤 프로젝트입니다. 사용자의 자연어 입력, 예를 들어 "얼큰한 국물 음식" 같은 표현을 태그로 변환하고, 메뉴와 식당을 추천하는 앱입니다.

프로젝트는 React Native 프론트엔드와 FastAPI 백엔드로 구성되어 있으며, 세 팀이 나누어 개발합니다.

- DB 팀: 성북구 일대 식당 283개와 메뉴 5,678개 크롤링 완료
- LLM 팀: 메뉴를 음식 종류(kind) 목록으로 정리하고, 14개 태그 부여 및 자연어 입력을 태그로 추출하는 `extract.py` 구현
- CF 팀: 행동 기반 추천 알고리즘 구현

이 모듈은 CF 팀의 독립 추천 모듈입니다. 초기 구현은 LLM과 DB에 직접 의존하지 않으며, 합성 데이터(list/dict)로 동작을 검증합니다. 이후 실제 시스템과 병합할 때 DB 연동이 쉽도록 데이터 접근부는 어댑터로 분리합니다.

## Input

- 사용자 행동 기록
- 음식 종류(kind)별 태그 데이터
- LLM이 반환했다고 가정한 태그 리스트

## Output

추천 메뉴 리스트를 두 탭으로 분리해 반환합니다. 각 추천 결과는 `score`, `matched_tags`, `reason`을 포함합니다.

- `tab1_results`: 기본추천 결과. 점수는 세션 기반 CF 점수입니다.
- `tab2_results`: 개인화추천 결과. 점수는 사용자 기반 CF 점수입니다.
- `tab2_empty_reason`: 탭 2가 빈 결과일 때의 원인 코드입니다.

탭 1과 탭 2의 점수는 의미가 다르므로 병합하지 않고 분리해서 노출합니다.

## Current Tab Structure

### 탭 1: 기본추천

탭 1은 "지금 이 검색과 비슷한 의도의 사람들이 무엇을 골랐나"에 답합니다.

- 함수: `recommend_tab1_default`
- 방식: 세션 기반 CF
- 현재 입력 태그와 과거 검색 세션의 입력 태그를 Jaccard 유사도로 비교
- 유사한 세션의 행동을 `click=1`, `final_select=2`로 누적해 메뉴 점수 계산
- 모든 사용자에게 작동하므로 콜드스타트에 강함
- 사용자가 이미 `final_select`한 메뉴는 제외

### 탭 2: 개인화추천

탭 2는 "나와 닮은 사용자들이 무엇을 골랐나, 내가 안 먹은 것 중에서"에 답합니다.

- 함수: `recommend_tab2_personalized`
- 방식: 사용자 기반 CF
- 사용자의 누적 행동 메뉴 집합으로 유사 사용자를 찾음
- 유사 사용자가 고른 후보 메뉴에 `유사도 * 행동 가중치`로 점수 부여
- 본인 행동 이력이 있어야 작동
- 사용자마다 다른 추천 결과를 반환
- 사용자가 이미 `final_select`한 메뉴는 제외

기존 콘텐츠 기반 태그 매칭 함수 `recommend_tab1`은 보류 상태입니다. 현재 메인 `recommend()`에서는 호출하지 않지만, 필요하면 나중에 다시 사용할 수 있도록 함수는 남겨 둡니다.

## Core Principles

1. 추천 단위는 개별 raw 메뉴가 아니라 음식 종류 `kind`입니다.
   예: "한식 김치찌개" 같은 가게별 메뉴가 아니라 "김치찌개"라는 추상 음식 종류를 추천합니다.

2. 비교 단위는 탭마다 다릅니다.
   - 탭 1 (기본추천): 검색 세션 단위입니다. "지금 이 검색"과 비슷한 과거 세션을 비교합니다. 같은 사용자도 검색마다 의도가 다를 수 있으므로 세션 단위로 봅니다.
   - 탭 2 (개인화추천): 사용자 누적 취향 단위입니다. "나라는 사람"과 닮은 사용자를 비교합니다. 사용자를 하나의 취향 덩어리로 봅니다.

   두 탭은 서로 다른 질문에 답합니다. 탭 1은 "지금 무엇을 원하는가", 탭 2는 "당신은 누구인가"를 담당합니다. 탭 1이 세션 단위로 현재 의도를 담당하므로, 탭 2는 사용자 단위로 단순화해도 시스템 전체로는 균형이 맞습니다.

3. 태그는 14개 고정 태그만 사용합니다.
   `따뜻한`, `시원한`, `바삭한`, `쫄깃한`, `진한`, `얼큰한`, `담백한`, `고소한`, `달달한`, `가벼운`, `국물있는`, `든든한`, `해장`, `야식`

4. 추천 결과는 두 탭으로 분리해서 노출하며 점수를 병합하지 않습니다.

5. 좋아요는 이번 데모 범위에서 제외합니다.

6. 사용자 행동은 클릭과 최종선택만 사용합니다.
   - 클릭: 1점
   - 최종선택: 2점

7. 합성 데이터는 LLM 팀의 고정 태그 vocabulary와 맞춰 검증합니다.

8. 데이터 소스는 어댑터 패턴으로 분리합니다. 현재는 합성 데이터를 사용하지만, 실제 DB 통합 시에는 데이터 접근부를 교체합니다.

## Tab 2 Personalized CF Details

탭 2는 4단계로 작동합니다.

```text
STEP 0: 유사 사용자 선정
STEP 1: 후보 필터
STEP 2: 후보 점수 계산
STEP 3: 정렬 후 top_k 반환
```

### STEP 0: 유사 사용자 선정

`_find_similar_users(user_id, min_similarity=0.1, max_users=20)`를 사용합니다.

- 사용자가 `click` 또는 `final_select`한 모든 kind를 집합으로 봅니다.
- 다른 사용자와 행동 메뉴 집합의 Jaccard 유사도를 계산합니다.
- 유사도 계산에는 행동 가중치를 쓰지 않습니다.
- `min_similarity` 이상인 사용자만 남기고, 유사도 내림차순으로 최대 `max_users`명 반환합니다.

현재 기본값은 합성 데이터 50명 기준 잠정값입니다.

- `min_similarity=0.1`: 닮음의 최소 기준
- `max_users=20`: 유사 사용자 상한

실 DB 통합 후에는 실제 유사도 분포를 보고 조정합니다. 예를 들어 사용자가 많아지면 `max_users`를 50~100 범위로 늘릴 수 있습니다.

### STEP 1: 후보 필터

`_filter_candidate_kinds(input_tags, user_id)`를 사용합니다.

입력 태그 필터는 AND 기반이며, 입력 태그가 많아질수록 살짝 완화합니다.

- 입력 태그 1개: 1개 매칭 필요
- 입력 태그 2개: 2개 전부 매칭 필요
- 입력 태그 3개 이상: N-1개 이상 매칭 필요

예를 들어 `["얼큰한", "국물있는"]`은 두 태그를 모두 가진 메뉴만 통과합니다. 그래서 `얼큰한`만 있고 `국물있는`이 없는 비빔국수는 후보에서 탈락합니다.

반면 태그가 3개 이상이면 모두 만족하는 메뉴가 드물 수 있어 한 태그까지 빠짐을 허용합니다. 이 경우 한 태그가 빠진 메뉴가 나올 수 있습니다.

또한 본인이 이미 `final_select`한 메뉴는 후보에서 제외합니다. `click`만 한 메뉴는 아직 최종 결정한 메뉴가 아니므로 후보로 남깁니다.

### STEP 2: 점수 계산

탭 2 점수는 입력 태그 유사도를 점수에 곱하지 않습니다. 입력 태그는 후보를 거르는 필터로만 쓰고, 점수는 유사 사용자의 행동으로만 매깁니다.

```text
탭 2 점수 = Σ (유사 사용자 유사도 × 그 사용자의 메뉴 행동 가중치)
```

- 유사도: STEP 0에서 계산한 사용자 간 Jaccard 유사도
- 행동 가중치: `click=1`, `final_select=2`
- 같은 사용자가 같은 메뉴에 여러 번 행동해도 그 사용자의 기여는 최대 가중치 하나만 반영합니다.

이렇게 필터(자격)와 점수(순위)를 분리합니다. 입력 의도는 필터가 지키고, 개인화는 점수가 담당합니다.

### STEP 3: 정렬

점수가 있는 후보만 남긴 뒤 다음 기준으로 정렬합니다.

1. `score` 내림차순
2. 동점이면 `kind_id` 오름차순
3. 상위 `top_k`개 반환

`top_k`는 최대 개수입니다. 후보가 `top_k`보다 적으면 있는 만큼만 반환합니다. 현재 메인 `recommend()`의 기본 `top_k`는 10입니다.

## Empty Results

탭 2는 본인 행동 이력이 있어야 작동합니다. 신규 사용자처럼 행동 이력이 없는 경우 탭 2가 빈 결과가 되는 것이 정상입니다. 이때 콜드스타트는 탭 1 기본추천이 담당합니다.

`tab2_empty_reason`은 다음 중 하나입니다.

- `None`: 정상 결과
- `no_history`: 행동 이력 자체가 없음
- `no_similar_users`: 행동 이력은 있으나 닮은 사용자가 없음
- `no_candidates`: 닮은 사용자는 있으나 조건에 맞는 메뉴가 없음

CF 모듈은 코드값만 반환합니다. 사용자에게 보여줄 안내 문구는 프론트엔드에서 사유별로 처리합니다.

## Function Notes

`recommend(input_tags, user_id, top_k=10)`는 두 탭을 모두 포함한 `RecommendationResponse`를 반환합니다.

`recommend_tab1_default()`는 추천 결과 리스트만 반환합니다.

`recommend_tab2_personalized()`는 `(results, empty_reason)` 튜플을 반환합니다. 다른 탭 함수와 반환 타입이 다르므로 외부에서 직접 호출할 때 주의해야 합니다.

- 정상: `(결과 리스트, None)`
- 빈 결과: `([], "no_history" | "no_similar_users" | "no_candidates")`

## Dependency Policy

초기 구현은 표준 라이브러리만 사용하고 외부 의존성을 최소화합니다.

## 향후 개선 방향 (실 데이터 누적 후)

현재 CF는 데모/합성 데이터 기준 설계입니다. 실 서비스에서 다음 항목을 검토합니다.

1. 검색 의도 반영 (`input_similarity`)
   - 현재: 유사 사용자의 메뉴 행동 전체를 봅니다.
   - 개선: 유사 사용자가 "비슷한 검색"에서 고른 메뉴에 가중치를 줄 수 있습니다.
   - 주의: 탭 1 세션 기반 추천과 차별성이 흐려지지 않게 균형이 필요합니다.

2. 태그 중요도 차등
   - 현재: 입력 태그 개수 기준 필터(1~2개 전부, 3개 이상 N-1)를 사용합니다.
   - 개선: `국물있는`, `해장` 같은 핵심 태그를 더 강하게 반영할 수 있습니다.
   - 필요: 어떤 태그가 핵심인지 사용자 데이터로 검증해야 합니다.

3. 유사 사용자 파라미터 조정
   - 현재: `min_similarity=0.1`, `max_users=20`입니다.
   - 개선: 실 데이터 유사도 분포를 보고 조정합니다.
   - 예: 사용자가 많아지면 `max_users`를 50~100 범위로 늘릴 수 있습니다.

4. 시간 가중치
   - 현재: 오래된 행동과 최근 행동을 동일하게 봅니다.
   - 개선: 최근 행동에 더 높은 가중치를 줄 수 있습니다.
   - 예: 최근 30일 1.0, 90일 0.7, 그 이전 0.4

5. click 신뢰도 차등
   - 현재: `click=1`, `final_select=2`입니다.
   - 개선: click 노이즈가 크다면 차이를 확대하거나, 체류시간 같은 신호로 click의 질을 구분할 수 있습니다.
   - 필요: 실 데이터에서 click 패턴 분석이 필요합니다.

6. DB 통합 시 ID 매핑
   - `FoodKind.kind_id`와 DB의 음식 종류 ID를 정확히 맞춰야 합니다.
   - ID가 어긋나면 CF 점수가 엉뚱한 음식에 붙습니다.
   - 어댑터에서 ID 변환을 명확히 처리해야 합니다.
